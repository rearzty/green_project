This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Контекст проекта

Хакатонный сервис автопроектирования городского озеленения с учётом отступов от инженерных сетей (задача, команда, таймлайн — в [README.md](README.md)). Ключевой факт, объясняющий многие решения в коде: **реальные данные организаторов открываются только 15.09.2026**, поэтому весь пайплайн сейчас разработан и проверен на синтетических территориях (`scripts/generate_synthetic_data.py` → `data/synthetic/*.geojson`, гитигнорится). Из-за этого некоторые вещи *намеренно* не захардкожены — см. раздел "Плейсхолдеры" ниже.

Подробности архитектуры, API-контракта, обоснований решений и истории изменений — в [docs/architecture.md](docs/architecture.md), [docs/api_contract.md](docs/api_contract.md), [docs/decision_log.md](docs/decision_log.md), [docs/worklog.md](docs/worklog.md).

## Команды

Python зафиксирован на 3.11 (`.python-version`) — на более новых версиях риск проблем со сборкой GDAL/Fiona/Shapely/pyproj.

```bash
pip install -e ".[dev]"                       # установка (backend + geo_engine + ml_scoring)

pytest                                        # все тесты
pytest tests/test_geo_engine/test_pipeline.py # один файл
pytest tests/test_geo_engine/test_pipeline.py::test_buildable_area_is_subset_of_territory  # один тест

python -m scripts.generate_synthetic_data     # тестовые территории -> data/synthetic/
python -m ml_scoring.train_synthetic          # обучить ML-скоринг (пишет ml_scoring/artifacts/model.joblib,
                                               # без него scoring_mode="ml" упадёт с ModelNotTrainedError)

python -m uvicorn backend.app.main:app --reload  # backend (нужен PostgreSQL+PostGIS, см. GREENPROJECT_DATABASE_URL)
```

Фронтенд (`frontend/`): `npm install`, `npm run dev`, `npm run build`, `npm run lint`.

Полный стек одной командой (собирает свежую ML-модель внутри образа при билде):
```bash
docker compose -f infra/docker-compose.yml up --build
```
backend + Swagger — `localhost:8000/docs`, frontend — `localhost:3000`.

Тесты лежат целиком в корневом `tests/` (зеркалит `geo_engine`/`ml_scoring`/API), не внутри `backend/`.

## Архитектура

Монорепо из трёх независимых Python-пакетов и одного слоя-склейки:

- **`geo_engine/`** — чистая геометрия, ноль импортов FastAPI/SQLAlchemy. Доменная модель в `model.py` (`Utility`, `Zone`, `PlantingCandidate`, `PlantingItem`).
- **`ml_scoring/`** — скоринг кандидатов, зависит только от `geo_engine.model`/`geo_engine.norms`, тоже без FastAPI/БД. Две взаимозаменяемые стратегии (`HeuristicScorer`, `MLScorer`) за одним интерфейсом `ScoringStrategy`.
- **`backend/app/services/pipeline_service.py`** — единственное место, где `geo_engine` и `ml_scoring` импортируются вместе. Это намеренно: оба пакета можно тестировать и использовать отдельно от сервера.

Порядок пайплайна (каждый шаг — реальная функция, не только концепция):
```
read (geo_engine/io/*) -> Utility/Zone (нормализация по слоям/полям)
  -> build_exclusion_zone + buildable_area (buffers.py)
  -> generate_candidates (candidates.py)
  -> ScoringStrategy.score (ml_scoring)
  -> greedy_select (placement.py)
  -> Plan/PlantingItemRow в БД -> GeoJSON на фронт / DXF через io/dxf_writer.py
```

**Backend — по-настоящему асинхронный, но не везде одинаково.** БД — `asyncpg`+`AsyncSession` (`backend/app/db/session.py`), все эндпоинты — `async def`. Но CPU-bound шаги (`geo_engine`-геометрия в `pipeline_service.generate_plan`, `edit_service.validate_plan`, DXF-парсинг/запись) остаются обычными **синхронными** функциями, которые роут вызывает через `fastapi.concurrency.run_in_threadpool` — если сделать их `async def` с синхронным CPU-кодом внутри, это заблокирует event loop на всё время вычисления (асинхронность реально помогает только на I/O, здесь — БД). Мультипроцессинг сознательно не используется — оверкилл для текущего масштаба.

**Ловушка async SQLAlchemy ORM, в которую здесь реально попали (дважды) — `sqlalchemy.exc.MissingGreenlet`.** Любое обращение к ленивой (не подгруженной eager'ом через `selectinload`) связи объекта — `plan.project`, `plan.items` и т.д. — требует await, который движок может сделать только изнутри "greenlet"-контекста активного `await session.execute(...)`; обычное обращение к атрибуту после `return`/`await service_call()` этот контекст не создаёт и падает с `MissingGreenlet`, а не тихо тормозит. Присвоение `plan.items = rows` (или `.append`) тоже не спасает — SQLAlchemy сначала пытается подгрузить *текущее* состояние коллекции для правильного cascade/diff, и падает так же. Рабочий паттерн — как в `api/deps.py::get_project_or_404`/`get_plan_or_404`: подгружать нужные связи через `select(...).options(selectinload(...))` заранее (для свежесозданных объектов — `pipeline_service.generate_plan` явно перезапрашивает `Plan` с `selectinload(Plan.items, Plan.project)` после `commit()`, а не пытается собрать связи руками).

**Соседняя ловушка (третий раз попались, на `ensure_materialized`) — `selectinload` молча не перезагружает уже загруженную (хоть и устаревшую) коллекцию.** `SessionLocal` тут с `expire_on_commit=False` (см. `db/session.py`) — значит `commit()` не инвалидирует уже загруженные атрибуты identity-mapped объекта. Если объект `Plan` в этой сессии уже когда-то подгружал `plan.items` (пусть даже пустым списком — как раз кейс "план ещё не материализован"), то повторный `select(...).options(selectinload(Plan.items))` для того же PK **не перезапросит** коллекцию — SQLAlchemy считает её "уже загруженной" и просто отдаёт тот же закэшированный (пустой) список, даже если в БД уже реально появились строки. Не падает — тихо возвращает не то. Фикс — `.execution_options(populate_existing=True)` на повторном select, форсирует перезаписать уже загруженные атрибуты/связи свежими данными из ответа. См. `pipeline_service.ensure_materialized()`.

**Ручная правка плана — WGS84 туда-обратно.** Правки (клик/drag-маркер `PATCH .../items/{id}`, удаление одной позиции `DELETE .../items/{id}`, структурированные операции `POST .../edit-structured` — убрать в радиусе/исключить полигон/заменить тип в зоне) приходят с фронта в WGS84 (родная CRS Leaflet), а хранится всё в `project.source_crs`. `geo_io.py::from_wgs84()` (симметрична `_to_wgs84()`) делает обратную перепроекцию перед сравнением/сохранением — раньше это было известным no-op багом (TODO в коде), пока `source_crs` никогда не был проставлен; сейчас `EPSG:32637` — дефолт в UI, так что баг стал бы реальным без этого фикса. `remove_within_radius`'s `radius_m` не перепроецируется (уже в метрах целевой CRS), перепроецируется только сама точка/полигон. `DELETE .../items/{item_id}` (`edit_service.delete_item`) намеренно не пишет `EditHistory` — так же, как уже делают `remove_within_radius`/`exclude_polygon` — запись со ссылкой на `planting_item_id`, который в этой же транзакции удаляется, никогда бы не пережила commit.

**Клик по дереву/кусту на карте — точечная правка одного элемента** (`frontend/components/MapView.tsx::bindPlanItemInteractions`), поверх уже существовавших массовых операций по области. Технический нюанс: посадки-точки раньше рендерились как `CircleMarker` (SVG `Path`, не `Marker`) специально потому, что дефолтная иконка `L.Marker` тянет image-файлы, которые бандлер не резолвит (см. `docs/worklog.md`) — но `Path`-слои не умеют drag без стороннего плагина. Решение — `L.divIcon` (иконка из чистого CSS-div, без внешних файлов) + обычный `L.marker(..., {draggable: true})`: получаем нативный drag Leaflet, ту же проблему с картинкой не возвращаем. `pointToLayer` создаёт маркер, `onEachFeature` вешает `dragend` (→ `PATCH` geometry) и попап с кнопками смены типа/удаления, собранный руками через `L.DomUtil`/`L.DomEvent` (Leaflet-попапы не рендерятся React-деревом). Правки одной точки идут по тем же эндпоинтам (`PATCH`/`DELETE .../items/{id}`), что и раньше существовавший, но не подключённый к фронту `PATCH`. Кнопки смены типа в попапе — только `tree`/`shrub` (не `lawn`): `lawn` в этом приложении всегда полигон (`generate_area_candidates`), у точечной позиции geometry так и останется `Point` — нашли живым тестом (клик → "Газон" → `planting_type="lawn"` с `geometry.type="Point"`, ничего не упало, просто мусорная комбинация). То же самое умеет создать и `replace_type_in_zone` (уже существовавшая операция) — там проверки нет, это отдельный, не почищенный сейчас технический долг.

**`<GeoJSON>` не переотрисовывает `data` при правке той же позиции плана — второй раз наступили на ту же грабли, что и с наложением слоёв при повторной загрузке.** `layersKey`/`planKey` (см. ниже) форсируют remount при смене *плана целиком* (другой `plan_id`), но drag/удаление/смена типа одной позиции — это **тот же** `plan_id` с другим содержимым `features`, так что до фикса правка на бэкенде проходила успешно, а карта эту правку не показывала (снятие/переигровка требует полного unmount `<GeoJSON>`, react-leaflet не диффит `data` реактивно). Правка — `frontend/app/page.tsx::planRevision` — счётчик, инкрементируется в `applyPlan()` при каждом `setPlan`, `planKey` строится как `` `${plan_id}:${planRevision}` ``, а не только `plan_id`. Задним числом это, похоже, чинит и старую (не проверенную визуально, только через API) недосказанность про структурированные операции — `убрать в радиусе`/`исключить полигон`/`заменить тип` тоже используют один и тот же `plan_id` для правки уже существующего плана.

**Повторный клик «Generate» с теми же настройками — не создаёт дубль в истории.** `pipeline_service._find_reusable_plan()`: если текущий (`is_current`) план проекта уже имеет тот же `scoring_mode` и тот же набор `planting_types`, и никто не редактировал его руками (`has_manual_edits`), `generate_plan` просто возвращает этот план заново (домате­риализуя, если он успел схлопнуться) вместо генерации нового. Намеренно ограничено только текущим планом, не всей историей — повторное использование произвольного старого плана рисковало бы незаметно подсунуть результат, посчитанный по уже изменившимся `planting_norms.yaml`/ML-модели, как будто он свежий (см. параграф про recipe-based хранение выше — версионирования рецепта под это нет).

**Сессия переживает обновление страницы — `localStorage`, не куки/аккаунт.** В приложении нет логина/пользователей, поэтому "запомнить последний проект" реализовано как `frontend/app/page.tsx`: `{projectId, planId}` в `localStorage` (ключ `greenproject:session`), перечитывается в `useEffect` на маунте и подтягивает свежие `project`/`plan`/`plans` с бэкенда заново (не кэширует сами данные — только два id, так что не может протухнуть тем же способом, что закэшированные данные). Невалидный/удалённый id просто тихо забывается (try/catch вокруг fetch). Кнопка «Очистить всё» в `ControlPanel.tsx` чистит только это — `localStorage.removeItem` + сброс React-state; в БД ничего не удаляет (это не то же самое, что `TRUNCATE` из раздела про dev-БД выше).

**История планов**: `GET /api/projects/{id}/plans` — каждый `generate` создаёт новый `Plan` (не перезаписывает предыдущий), `is_current` двигается на новый. Раньше фронт держал в состоянии только последний план — эвристика и ML на разных generate выглядели как «путаница»; теперь `ControlPanel.tsx` показывает список всех планов проекта (режим/время/кол-во позиций), клик — `getPlan()` и переключение отображаемого плана.

**`Plan` хранит рецепт, а не обязательно построчные данные** (`backend/app/db/models.py::Plan`, `backend/app/services/pipeline_service.py`): `generate_plan` — чистая функция от (слои проекта, `planting_norms.yaml`, ML-артефакт, `Plan.scoring_mode`/`Plan.planting_types`) — рандома в `geo_engine`/инференсе `ml_scoring` нет (только офлайновый `train_synthetic.py`). Значит, план, который никто не редактировал руками, побитово воспроизводим — не обязательно держать его `planting_items` (потенциально сотни тысяч строк на реальном масштабе) в БД вечно. `pipeline_service._prune_stale_plans()` вызывается при каждом `generate_plan` и удаляет построчные данные (`Plan.materialized = False`) у всех планов проекта, кроме нового текущего и тех, где `Plan.has_manual_edits = True` (руками отредактированное — уже не рецепт, а реальные данные, не восстановить пересчётом). `backend/app/api/deps.py::get_plan_or_404` — единая точка входа для всех роутов, принимающих `plan_id` (get_plan, patch_item, edit-structured, validate, export): если `plan.materialized` ложно, прозрачно вызывает `pipeline_service.ensure_materialized()` (пересчитывает `_compute_planting_rows` и вставляет заново, ~1-2с на реальном масштабе) до того, как роут увидит план — сами роуты не знают, был план схлопнут или нет. `Plan.item_count` — снятый в момент генерации/правки снэпшот количества позиций, читается `list_plans` напрямую (не `COUNT`-join — он бы показывал 0 у всех схлопнутых планов). Если меняешь логику `apply_item_patch`/`apply_structured_edit` — не забудь проставлять `plan.has_manual_edits = True` при первой реальной правке и корректировать `plan.item_count` при удалении позиций, иначе `_prune_stale_plans` может стереть только что отредактированные данные при следующем `generate`.

Нормативы — конфиг, не код: `geo_engine/config/planting_norms.yaml`, читается через `geo_engine/norms.py::load_norms()`. Значения — черновик из текста задания, ждут сверки по полному ТЗ 15.09.

**`zone_type="territory"` — обязательный межмодульный контракт**: `pipeline_service._territory_polygon()` ищет ровно эту зону, чтобы найти границу участка, и все ридеры обязаны её производить единообразно (`shp_geojson_reader`/`generate_synthetic_data.py` — напрямую через `object_type="territory"`, `dxf_reader.DEFAULT_LAYER_MAP` — слой `BOUNDARY`). Раньше DXF-слой `BOUNDARY` маплился в `zone_type="boundary"`, из-за чего DXF-импорт вообще не мог сгенерировать план (`_territory_polygon` не находил зону) — если добавляешь новый ридер или layer_map, следи, чтобы граница участка выходила именно как `"territory"`.

**`buildable_area()` — твёрдые препятствия vs отступы**: `building`/`road`/`existing_greenery` (`buffers.HARD_OBSTACLE_ZONE_TYPES`) вычитаются из buildable-территории по точной геометрии, а не буфером-отступом — кандидат физически не может оказаться внутри уже существующей зелени. `ml_scoring`'овский `existing_greenery_gap_score` работает поверх этого как мягкий ранжирующий фактор (предпочесть больший отступ среди уже легальных кандидатов), а не как замена жёсткому исключению.

**`planting_type` ↔ геометрия — тоже жёсткий контракт**: `lawn` везде в пайплайне — это полигон (`generate_area_candidates` делает из него целый суб-полигон buildable-территории), `tree`/`shrub` — всегда точка (`generate_point_candidates`, сетка). Ручные правки (`backend/app/services/edit_service.py::apply_item_patch` и `apply_structured_edit`'s `replace_type_in_zone`) — единственное место, где `planting_type` можно сменить без пересчёта геометрии, поэтому именно там `_assert_planting_type_matches_geometry()` отклоняет (`PlantingTypeGeometryMismatchError` → HTTP 400 в `routes_edit.py`) любую смену типа, которая рассинхронит `planting_type` и `geometry.geom_type` — иначе получается комбинация (например, `planting_type="lawn"` с `geometry.type="Point"`), которую ничего дальше по пайплайну (`ml_scoring`, DXF-экспорт) не ожидает. Баг был живьём воспроизведён через попап на точечном объекте на карте.

**Геометрия в БД (`backend/app/db/models.py`)**: колонки — `Geometry(geometry_type="GEOMETRY", srid=0)`, намеренно без фиксированного SRID, потому что CRS каждого проекта заранее неизвестна. `Project.source_crs` (свободный текст) хранит, в какой CRS реально лежит геометрия проекта; перепроекция в WGS84 для GeoJSON делается в `backend/app/services/geo_io.py::_to_wgs84()` через `pyproj.Transformer` напрямую, а не через PostGIS SRID transform.

**Известный пробел**: `geo_engine/crs.py::ensure_metric_crs()` (авто-определение UTM-зоны и репроекция в метрическую CRS) написана, но нигде не вызывается в реальном потоке — `project_service.create_project_from_file()` кладёт геометрию как есть. Пока всё на синтетике (уже в метрах) это не страшно, но до доверия к буферам на реальных геоданных это нужно подключить.

**Производительность `candidates.py`/`placement.py` рассчитана на реальный масштаб, не только на синтетику 100×80м**: на территории ~1.5×1.5км (реальные данные с data.mos.ru, `data/samples/`) `greedy_select` изначально зависал на часы (попарная проверка пересечения с каждым уже отобранным элементом — `O(n×k)`), а `generate_point_candidates` — на минуты (питоновский цикл с `Point(...).contains(...)` на каждую точку грида). Оба переписаны: `placement.py` — на равномерный пространственный хэш (ячейки по `canopy_radius_m`, с фолбэком на прямой перебор для редких крупных footprint'ов вроде полигона газона), `candidates.py` — на векторизованные вызовы `shapely.contains`/`shapely.distance` по всей сетке разом. Замер на 174K кандидатов: `greedy_select` часы → 21с; на 2.24M кандидатов кустарника: `generate_point_candidates` — минуты → 18.8с.

**Плотность кустарника — исправлено, было продуктовой, не технической проблемой**: изначально `shrub_default` был `min_distance_m=1.0, canopy_radius_m=0.5` — диаметр кроны (`canopy_radius_m*2=1.0`) в точности равнялся шагу сетки кандидатов (`candidates.py` сэмплирует `buildable_area` с шагом `min_distance_m`), так что реальная проверка пересечения крон в `greedy_select` (`placement.py`, буферизует каждую точку на `canopy_radius_m` и проверяет intersects с уже отобранными) почти ничего не отсеивала — получался практически сплошной ковёр из кустов на любой свободной площади (2739 шт. на демо-территории 100×80м, ~200K на реалистичной 640×640м). Пользователь увидел результат на демо-территории и явно попросил исправить. Починено подъёмом обоих значений пропорционально — `min_distance_m=3.0, canopy_radius_m=1.5` (то же отношение 2:1, что и у `tree_default`) — реальный радиус кроны куста стал достаточным, чтобы отбор по пересечению кругов по-настоящему отсеивал сетку: 299 шт. вместо 2739 на той же демо-территории. `ml_scoring/artifacts/model.joblib` переобучается автоматически при `docker compose up --build` (Dockerfile.backend гоняет `train_synthetic` после `COPY geo_engine`, слой инвалидируется при любом изменении `planting_norms.yaml`).

**Frontend**: `frontend/lib/api.ts` — единый типизированный клиент под весь API-контракт. `frontend/components/MapView.tsx` подгоняет вид карты под фактические данные (`FitBounds`), а не центрируется на фиксированную точку — не возвращай туда хардкод центра, это уже приводило к багу (карта заливкой на весь мир), см. `docs/worklog.md`.

**Синтетика привязана к реальной точке на карте**: `scripts/generate_synthetic_data.py::ANCHOR_LONLAT` сдвигает сгенерированную территорию (EPSG:32637/UTM 37N, метры) к реальным координатам в центре Москвы — чисто чтобы на демо-карте она попадала в узнаваемое место, а не в (0, 0). Сами объекты (сети/здания/зонирование) вымышлены, но раскладка правдоподобна: сети — пучком вдоль дороги (как реально прокладывают в траншее), здания — вдоль заднего края (как реальный двор), клумба существующей зелени — у входа в здание, не в чистом поле. `ControlPanel.tsx`'s поле CRS по умолчанию — `EPSG:32637`, под эту синтетику; при переходе на настоящие данные 15.09 замени/очисти.

**CORS**: `settings.cors_origins` разрешает и `localhost:3000`, и `127.0.0.1:3000` — браузер считает их разными origin, хотя это одна машина; забыть один из двух даёт молчаливый `TypeError: Failed to fetch` в браузере без единой строчки в логах backend (запрос туда не долетает).

**`validate_plan()` (`edit_service.py`) сравнивает площадь пересечения, не `intersects()`**: полигон газона (`buildable_area()`) по построению всегда касается границы зоны отступа — `intersects()` считает касание нарушением, `_violates_setback()` — нет (для точек-деревьев/кустов `intersects` по-прежнему корректен, там это не проблема).

**Буферы отступов считаются с `quad_segs=32`** (`buffers._BUFFER_QUAD_SEGS`), не дефолтным `quad_segs=8` — при мелких (0.3-0.5м, как у `lawn`) отступах погрешность аппроксимации круга полигоном шейпли на дефолтном разрешении сопоставима с самим отступом (доли миллиметра-миллиметр на непрямоугольных стыках/торцах буфера) и тесты на реальное расстояние до сети это ловят.

**Буфер зоны (`building`/`road`) — `join_style="mitre"`, буфер сети (`utility`) — обычный `round`**: у shapely `buffer()` по умолчанию скругляет все углы — для здания это давало на карте буквально скруглённые "блинчатые" углы вместо прямоугольного отступа (нашёл пользователь по скриншоту — "явно не норм") и раздувало полигон дырки с 5 точек до ~130 (сглаживание окружности на `quad_segs=32`). Для сети (линии, могут гнуться) круглый отступ — физически верная форма клиренса вокруг трубы/кабеля, там `join_style` не трогали.

**`generate_plan` пишет посадки Core bulk INSERT (`sqlalchemy.insert(PlantingItemRow), rows`), не ORM `session.add_all()`**: замерено — 2746 строк через `add_all()`+`commit()` уходит 7.6с (~2.5мс/строка, батчинг INSERT'ов не срабатывает), одним bulk-запросом — доли секунды вне зависимости от количества строк. Это и есть причина «долго грузит» на реальной территории — геометрия (`geo_engine`) считалась за <1с, всё время уходило на запись в БД. `geo_io.py::domain_item_to_row_values()` — версия `domain_item_to_row()`, отдающая plain dict (с явно сгенерированным `id`) вместо ORM-объекта, для этого bulk insert'а.

**Локальная dev-БД всё ещё может распухнуть — чисти её, если `/generate` вдруг "тормозит" без видимой причины в коде.** До введения recipe-based хранения планов (см. выше) каждый клик «Generate» безусловно писал построчно весь результат навсегда — разово нагнали 1.5 млн строк (553 МБ) за один день тестирования, `insert+commit` в `generate_plan` вырос с 0.2с до 3.7-8.4с (`planting_items` — PK на случайном UUID, вставка в такую таблицу у Postgres линейно замедляется с фрагментацией B-tree индекса при росте). Теперь `_prune_stale_plans` держит материализованными только текущий план и руками отредактированные — но много проектов (каждый со своим текущим планом) или много руками отредактированных планов всё ещё накапливают реальные данные, это осознанный компромисс, не баг. Почистить всё целиком (только dev, не продакшен):
```bash
docker compose -f infra/docker-compose.yml exec db psql -U greenproject -d greenproject -c "TRUNCATE edit_history, planting_items, plans, layers, projects CASCADE;"
```

**`ScoringStrategy`/`geo_engine.placement.ScoreFn` — batch-скоринг, не по кандидату**: `score_fn(candidates: list[...]) -> list[(score, rationale)]`, не `score_fn(candidate)`. `MLScorer.score_batch()` делает один векторизованный `pipeline.predict_proba()` на весь список сразу — по кандидату отдельно замерено втрое медленнее (~5300 кандидатов кустарника: 9.5с против 0.8с батчем) из-за накладных расходов sklearn на каждый отдельный вызов. `HeuristicScorer` batch не переопределяет — дефолтная реализация (`ScoringStrategy.score_batch`) просто зовёт `score()` в цикле, там это дёшево и без sklearn-overhead. Если пишешь свой `score_fn` напрямую (как в тестах) — не забудь новую сигнатуру.

## Плейсхолдеры — не "чинить" на конкретные значения без вопроса пользователю

- `geo_engine/io/dxf_reader.py::DEFAULT_LAYER_MAP` — соответствие "имя слоя DXF → object_type/zone_type" придумано для синтетики, реальные имена слоёв Мосгеотреста неизвестны до 15.09.
- `type_field` в `shp_geojson_reader.py::read_vector_file()` — то же самое для GeoJSON/SHP.
- CRS нигде не захардкожена как МСК-77/UTM — см. пробел выше.
- Точные значения в `planting_norms.yaml` — черновик, не итог. `lawn`-отступы (0.3-0.5м, кроме `power_line_corridor` — там сознательно 0.0, газон под ЛЭП обычно разрешён в отличие от деревьев) не 0.0 по прямой просьбе пользователя ("сделай примерное реалистичное значение"), не то же самое что "сверено по ТЗ".
