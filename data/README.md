# data/

- `synthetic/` — сгенерированные тестовые территории (`python -m scripts.generate_synthetic_data`), не коммитятся (см. `.gitignore`), нужны только локально для прогона пайплайна до открытия реальных данных 15.09.2026. Координаты — EPSG:32637 (UTM 37N), геометрия привязана (`ANCHOR_LONLAT` в скрипте) к реальной точке в центре Москвы (район Чистых прудов) исключительно для того, чтобы territory на демо-карте попадала в реальный, узнаваемый город, а не в (0, 0) — сами объекты (сети, здания, зонирование) полностью выдуманные, это не данные Мосгеотреста. При загрузке через UI/`ControlPanel` поле CRS уже стоит `EPSG:32637` по умолчанию для этой синтетики; для настоящих данных 15.09 его нужно будет поменять/очистить.
- `samples/` — примеры реальных геоданных (не синтетика). DXF-чертежи с коммуникациями от организаторов/Мосгеотреста появятся 15.09; уже сейчас здесь лежат реальные слои с data.mos.ru (см. ниже).

## data.mos.ru — уже подключено, есть реальные данные в `data/samples/`

Портал (`data.mos.ru`) доступен анонимно для чтения каталога (1246 наборов), но выгрузка через API (`apidata.mos.ru/v1`, см. `Документация API` в личном кабинете) требует персональный `api_key` — получается регистрацией в личном кабинете, программно завести аккаунт нельзя. Лицензия данных — Creative Commons Attribution 4.0 (см. подвал портала).

Первый заход нашёл только два датасета (по узким ключевым словам) — второй, более широкий проход по всем 1246 наборам (публичный `POST https://data.mos.ru/api/v2/odata/datasets/search`, тоже без `api_key`, отдаёт список/метаданные всех наборов с полем `hasGeo`) нашёл заметно больше:

- **id 2941 "Объекты капитального строительства"** — реестр строящихся/введённых объектов (адрес, площадь застройки, статус). `/features` отдаёт только **точку**-центроид, не полигон — поле `PolygonsCoordinates` на практике пустое. `data/samples/mos_ru_2941_capital_construction_raw.geojson` — сырая выгрузка (2063 записи, весь город).
- **id 2450 "Состояние зелёных насаждений"** — точки контрольных площадок наблюдения за озеленением (284 записи, весь город). `data/samples/mos_ru_2450_greenery_condition_raw.geojson` — сырая выгрузка.
- **id 64036 "Дворовые территории"** — реальные полигоны дворов (`MultiPolygon`) с адресом, площадью, балансодержателем. Единственный найденный набор, дающий **настоящую** (не аппроксимированную) границу небольшого благоустраиваемого участка — то, что нам реально нужно для `territory`.
- **id 60562 "Адресный реестр объектов недвижимости города Москвы"** — реальные полигоны **зданий** (`MultiPolygon`, не центроид, в отличие от id 2941), с `UNOM`/адресом/типом объекта.
- **id 1497 "Земельные участки в собственности города Москвы и неразграниченной собственности"** — реальные кадастровые границы участков (`CadastralNumber`, `PermittedUse`, площадь) — то самое «границы участков», упомянутое в задании как то, что якобы даёт data.mos.ru.
- **id 63181 "Газоны"** — реальные полигоны газонов (`MultiPolygon`) из АИС «Реестр зелёных насаждений».
- Полноценного открытого слоя подземных инженерных сетей на портале **по-прежнему нет** ни под одним из проверенных ключевых слов (`инженер`, `сет`, `труб`, `кабел`, `водопровод`, `тепло`...) — это ожидаемо, такие данные даёт хакатон отдельно 15.09 (см. `docs/decision_log.md`). OpenStreetMap (см. ниже) даёт тот же результат — в центре Москвы сети подземные, на поверхности не отображены.

**Важное ограничение API, из-за которого выше все — полигональные наборы, а не привязанные к конкретному месту**: `GET .../datasets/{id}/features?bbox=...` — пространственный фильтр по прямоугольнику — **работает только для точечных наборов** (задокументировано на `data.mos.ru/developers/documentation`, раздел «Получение геоданных»; проверено эмпирически на дворах/зданиях/газонах/участках — параметр молча игнорируется). Полей с районом/адресом для `$filter` (OData v2) тоже нет для вложенных `attributes.*`. Значит выбрать «двор рядом с точкой X» через API нельзя — приходится тащить пачку записей (`$top`, максимум 1000 без `$skip`) и там, где нужна привязка к конкретному месту, комбинировать с другим источником, у которого пространственный фильтр есть (см. ниже).

`data/samples/real_moscow_chistye_prudy.geojson` — самый первый тестовый участок (тот же формат `object_type`, что и синтетика), собранный из id 2941/2450 в районе Чистых прудов (тот же `ANCHOR_LONLAT`, что в `scripts/generate_synthetic_data.py`). **Ограничение:** координаты точек реальные, но полигоны зданий/зелени — квадраты/буферы, подогнанные под `DevelopmentArea`/фиксированный радиус, не настоящий контур (у id 2941/2450 просто нет полигональной геометрии) — у каждой фичи стоит `"footprint_is_approximated": true`. Пользователь справедливо указал, что это не похоже на реальную схему. Загружать с `source_crs=EPSG:32637`.

`data/samples/real_moscow_courtyard.geojson` — второй, заметно более реалистичный тестовый участок, собранный гибридно и покрывающий **все** `zone_type`, которые пайплайн реально понимает (`geo_engine/buffers.py`), кроме инженерных сетей:
- `territory` — настоящий двор из id 64036 (Даниловский район, Мытная ул., реальная неправильная форма, 4110 м², реальный балансодержатель) — координаты нельзя было подобрать под конкретное место (см. ограничение bbox выше), поэтому просто взят один хорошо оформленный реальный двор из выборки.
- `building`/`existing_greenery` — не из data.mos.ru (для них пространственный поиск «рядом с этим двором» через API невозможен), а из **OpenStreetMap Overpass API** (`overpass-api.de/api/interpreter`, полностью открытый, без ключа, **с рабочим bbox-фильтром**) — 17 настоящих контуров зданий и 2 настоящих зелёных зоны в радиусе 80м от двора (буфер строился в EPSG:32637, не в градусах).
- `road` — тоже из OSM (`highway=motorway|trunk|primary|secondary|tertiary|unclassified|residential|service`), в радиусе 120м. OSM-линии без ширины — реальная геометрия только осевая линия, поэтому каждая буферизуется на половину ширины по типу (`ROAD_HALF_WIDTH_M` в скрипте сборки: service 2м, residential/unclassified 3м, tertiary 4м, secondary 5м, primary 6м) и обрезается контекстным буфером — иначе полоса тянулась бы на весь квартал. 45 сегментов (OSM режет улицу на куски на каждом перекрёстке/съезде — это нормально, не дубли). `road` — уже полноценно поддержанный тип в `planting_norms.yaml` (`setbacks_m.road`) и `HARD_OBSTACLE_ZONE_TYPES` — код трогать не пришлось, не хватало только геометрии. Пешеходные дорожки (`highway=footway/path`) сознательно **не** включены — для них нет отдельного норматива-отступа, а прогонять через тот же `road` (отступ дерева 2м) съело бы неоправданно много места на маленьком дворе под то, что по факту метровая тропинка.
- `zoning` — тоже из OSM (`landuse=residential/industrial/commercial/retail`, `leisure=park`), смаплено в словарь `zoning_suitability` из `planting_norms.yaml` (`residential`/`industrial`/`public`/`recreational`) через `properties.zoning_category` — именно это имя атрибута читает `geo_engine/candidates.py::_zoning_at()`, не то, что могло бы показаться логичным на вид (`zoning_type` изначально написал неправильно, поймано до сдачи). Найдено 2 полигона (жилая застройка), пересекающих контекст 120м вокруг двора. **Геометрия НЕ обрезается по контексту**, в отличие от дорог/зданий — первая версия обрезала пересечением с круглым буфером и рисовала на карте кусок настоящей границы квартала пополам с дугой окружности (пользователь заметил на скриншоте: явно скруглённый, ничему на местности не соответствующий край) — поймано сравнением числа вершин (сырой полигон OSM — 9-39, обрезанный — 31-45, с лишними точками ровно по дуге буфера). Зонирование — не препятствие, а фон для скоринга, ему не нужна точная граница по масштабу проекта, поэтому теперь берётся полностью как есть, даже если тянется на весь квартал. Из-за этого `MapView.tsx`'s прямоугольник границ рабочей области (`extentBounds`) специально исключает `zoning` из расчёта — иначе рамка раздувалась бы на весь квартал вместо реального периметра проекта.
- Итог — двор неправильной формы среди настоящих домов на настоящей улице, с настоящими дорогами и зонированием, а не квадрат в квадрате. Загружать **без указания CRS** — файл в чистом WGS84 без `crs`-члена, автоматически определяется и репроецируется при загрузке (см. `ensure_metric_crs()` в `CLAUDE.md`). Реально влияет на план, не только на картинку: с дорогами план ужался с 182 до 108 позиций — раньше часть кустов ложилась прямо на проезд внутри двора.
- Коммунальных сетей здесь по-прежнему нет — ни один открытый источник их не даёт, включая OSM (проверено ещё раз этим же проходом).

**Ещё два реальных двора, тем же рецептом, для разнообразия районов** — код сборки вынесен в параметризуемую функцию (`build()` в скрипте сборки, одна и та же логика на вход разных courtyard/OSM-выгрузок):
- `data/samples/real_moscow_courtyard_gagarinsky.geojson` — Гагаринский район, Ломоносовский проспект, д.3к3 (3611 м²), рядом с МГУ/Воробьёвыми горами. 18 зданий, 32 дорожных сегмента, 2 зоны, **0 существующей зелени** (в радиусе 80м у OSM не нашлось травы/садов/леса с нужными тегами — честный результат, не баг).
- `data/samples/real_moscow_courtyard_biryulevo.geojson` — район Бирюлёво Восточное, Липецкая ул., д.28 (5133 м²) — типовая застройка, сильно отличается по характеру от двух предыдущих (панельные дома, больше открытого пространства между корпусами, рядом настоящая школа №902 и пруд). 6 зданий, 1 зелёная зона, 31 дорожный сегмент, 1 зона.
- Оба прогнаны через весь пайплайн: автоопределение CRS отработало на обоих без единого ручного указания, планы сгенерировались (172 и 317 позиций соответственно), геометрия валидна (проверено `shapely.is_valid` на каждой фиче).
- Выбирались из уже скачанной выборки 100 дворов (`courtyards_sample100.json` в скрэтче) по признаку «разные районы, разная площадь» — не самые первые попавшиеся, чтобы застройка визуально отличалась (плотный центр у Гагаринского vs. типовой микрорайон у Бирюлёво).

Ключ (`api_key`) для `apidata.mos.ru` — личный, пользовательский, **никогда не пишется в файлы репозитория** (используется только инлайново в разовых запросах). Каталог (`/datasets`, `/datasets/{id}`) и метаданные читаются без ключа; `api_key` нужен только для самих `/features`/`/rows`.

## Открытые источники, которые ещё стоит посмотреть (до 15.09)

- data.mos.ru — категория "Улично-дорожная сеть" на предмет цельного слоя геометрии проезжих частей (с ходу не нашли, есть только точечные наборы вроде выделенных полос/светофоров) — не критично, OSM `highway=*` уже закрывает это (см. `real_moscow_courtyard.geojson`).
- Пешеходные дорожки/тротуары (`highway=footway|path`) внутри территории — сознательно не подключены (см. выше, нет своего норматива-отступа) — если понадобятся, нужен сначала отдельный setback в `planting_norms.yaml`, не просто геометрия.
- id 3083 "Участки межевания жилых кварталов" и id 1497 (кадастровые участки) — не собраны в тестовый файл, но подтверждены рабочими (`hasGeo`, реальная полигональная геометрия) — годятся как альтернатива дворам для `territory`.
- Публичные учебные/демонстрационные DXF-чертежи инженерных сетей — для обкатки `geo_engine/io/dxf_reader.py` до появления реальных примеров от организаторов.
