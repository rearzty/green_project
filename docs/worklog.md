## 2026-09-10 — Ревизия пайплайна: два реальных бага (не плейсхолдеры), найдены и исправлены

Контекст: по просьбе пользователя Claude-сессия прошлась по всему пайплайну в поисках ошибок (не только известных плейсхолдеров из `CLAUDE.md`). Нашла и исправила два бага, воспроизводимых уже на синтетике — оба не были пойманы юнит-тестами, потому что ни один тест не гонял ридер до `generate_plan`.

- **DXF-импорт не мог сгенерировать план.** `dxf_reader.DEFAULT_LAYER_MAP` мапил слой `BOUNDARY` в `zone_type="boundary"`, а `pipeline_service._territory_polygon()` ищет ровно `"territory"` — GeoJSON/SHP-путь работал только потому, что `generate_synthetic_data.py` проставляет `"territory"` напрямую, это нигде не было общим контрактом. Починено: `BOUNDARY` теперь маплится в `"territory"` (см. `CLAUDE.md`). Регрессия: `test_dxf_boundary_layer_imports_as_territory_zone`.
- **`existing_greenery` не исключался геометрически.** Использовался только как мягкий признак скоринга (`existing_greenery_gap_score`, вес 0.15) — `buildable_area()` считала твёрдыми препятствиями только `building`/`road`, так что кандидаты на посадку могли оказаться внутри уже существующей зелени (воспроизведено на синтетике: 2 из 179 кандидатов на дерево попадали внутрь полигона `existing_greenery`). Починено: `existing_greenery` добавлен в `buffers.HARD_OBSTACLE_ZONE_TYPES`. Регрессия: `test_buildable_area_excludes_existing_greenery`. `ml_scoring/artifacts/model.joblib` переобучен (`python -m ml_scoring.train_synthetic`) под новую геометрию `buildable_area`.

## 2026-09-10 — Синтетика на реальной карте, реальные данные с data.mos.ru, фикс двух перф-багов

Контекст: пользователь не мог нормально протестировать — старая синтетика лежала в локальных метровых координатах от (0,0), которые без CRS интерпретировались как градусы и улетали в бессмысленную точку на карте.

- **Синтетика привязана к реальной точке.** `scripts/generate_synthetic_data.py` теперь сдвигает сгенерированную территорию (EPSG:32637/UTM 37N) к реальным координатам у Чистых прудов (`ANCHOR_LONLAT`) — объекты по-прежнему выдуманы, но участок теперь рисуется поверх настоящих улиц Москвы. `ControlPanel.tsx`'s поле CRS по умолчанию — `EPSG:32637`, под эту синтетику. Проверено вручную в браузере и через реальный `docker compose`-стек.
- **Разведка data.mos.ru + реальные данные.** Портал доступен анонимно для чтения каталога (1246 наборов); полноценный слой подземных сетей на нём отсутствует (ожидаемо, это дают организаторы 15.09), но есть два геопривязанных набора — id 2941 «Объекты капитального строительства» и id 2450 «Состояние зелёных насаждений». Пользователь дал личный API-ключ (`apidata.mos.ru/v1`, не закоммичен) — оба набора выгружены целиком в `data/samples/mos_ru_*_raw.geojson`, и собран маленький готовый к загрузке реальный тестовый участок `data/samples/real_moscow_chistye_prudy.geojson` (точки реальные, полигоны зданий/зелени — approximated, см. `data/README.md`).
- **Найдены и починены два реальных перф-бага** при стресс-тесте на территории ~1.5×1.5км (собранной из реальных данных выше): `geo_engine/placement.py::greedy_select` (попарная проверка со всеми уже отобранными — O(n×k), часы на 174K кандидатов) и `geo_engine/candidates.py::generate_point_candidates` (питоновский цикл `Point(...).contains(...)` на грид — минуты на 2.24M точек кустарника). Первый переписан на пространственный хэш по ячейкам, второй — на векторизованные вызовы shapely по всей сетке разом. Замеры: `greedy_select` — часы → 21с на 174K кандидатов; `generate_point_candidates` — минуты → 18.8с на 2.24M. Подробности контракта — в `CLAUDE.md`. Регрессия: полный `pytest` (13/13, geo_engine-часть теперь и быстрее — 45с вместо 89-158с).
- **Не починено, задокументировано как открытый вопрос**: даже с этими фиксами шаг сетки для `shrub` (`min_distance_m`=1м) даёт на территории 640×640м ~400K кандидатов и ~200K реально отобранных кустов — не баг производительности (оба шага быстрые), а вопрос продуктового смысла такого количества позиций в одном плане. Пользователь решил: territory просто размечается как buildable, полная автогенерация плана — отдельное явное действие (кнопка) на будущее, не тюнинг норматива сейчас. См. `docs/decision_log.md`.
- **3 примера входных DXF.** `scripts/generate_synthetic_data.py` теперь пишет и `.dxf` (не только `.geojson`) для каждой из 3 сид-территорий — слои соответствуют `DEFAULT_LAYER_MAP`, включая `BOUNDARY`→`territory`. Проверено полным циклом через живой `docker compose`-стек: загрузка `.dxf` → `generate` → `HTTP 200`, 2754 позиции. `data/synthetic/*.dxf` гитигнорится, как и `*.geojson`.
- **«failed to fetch» при загрузке через UI — найдена настоящая причина: CORS.** Первая гипотеза (окно пересборки backend-контейнера) оказалась неверной — реальная причина в том, что пользователь открыл фронтенд через `http://127.0.0.1:3000`, а `settings.cors_origins` разрешал только `http://localhost:3000`. Для браузера это разные origin даже на одной машине, поэтому CORS блокировал запрос ещё до отправки — отсюда и пустые логи backend (запрос туда не долетал). Починено: `backend/app/core/config.py` и `infra/docker-compose.yml` теперь разрешают оба origin. Проверено `curl -X OPTIONS` с обоими `Origin`-заголовками — оба получают корректный `access-control-allow-origin` в ответ.

## 2026-09-11 — Реалистичность синтетики, ложные нарушения норматива, наложение слоёв на карте

Контекст: пользователь посмотрел на реально сгенерированный план в браузере и не поверил — выглядело так, будто отступы от сетей/зданий не соблюдаются вообще, плюс `/validate` постоянно ругался на `lawn`, плюс несколько загрузок подряд накладывались друг на друга на карте.

- **Отступы для tree/shrub — проверено численно, работают правильно.** Написал проверку фактического расстояния от каждого отобранного элемента до каждой сети/здания против норматива (не на глаз) — 0 нарушений по всем 3 сидам синтетики. Закреплено тестом `test_selected_items_respect_every_setback_distance`.
- **`lawn: 0.0` для всех сетей/зданий в `planting_norms.yaml` — было намеренным черновым значением, не багом**, но выглядело неубедительно и пользователь попросил примерные реалистичные значения. Проставлено 0.3-0.5м (кроме `power_line_corridor` — там 0.0 оставлено осознанно, газон под ЛЭП — стандартная рекомендуемая практика в отличие от деревьев). Это тоже черновик, ждёт 15.09.
- **Найден и починен реальный precision-баг, который это же вскрыло**: на мелких (0.3-0.5м) отступах погрешность аппроксимации круга буфера шейпли (`quad_segs` по умолчанию 8) стала сопоставима с самим отступом — тест ловил кандидата на 0.36мм ближе норматива. Починено повышением `quad_segs` до 32 в `buffers.py` (реальная погрешность упала до 0.15мм), тест соответственно получил реалистичный допуск 1мм вместо 1e-6.
- **`validate_plan()` — починен false positive**, см. запись от 2026-09-10 (перенесено сюда как часть той же проверки: `_violates_setback()` теперь сравнивает площадь пересечения для полигонов, не факт касания).
- **Раскладка синтетики сделана более правдоподобной**: сети — параллельным пучком вдоль дороги (как в реальной траншее), не диагональными линиями через всю территорию; здания — вдоль заднего края (как реальный двор), не вразброс; существующая зелень — клумба у входа в здание. Геометрически проверено (нет наложений, всё в границах) и через весь пайплайн (0 нарушений на новой раскладке).
- **Наложение слоёв на карте при повторных загрузках — найдена причина и починена**: `react-leaflet`'s `<GeoJSON>` не переотрисовывает фигуры при смене `data` без `key` — его не было. `MapView.tsx` теперь получает `layersKey`/`planKey` (id проекта/плана), старые фигуры корректно снимаются. Заодно добавлены два переключателя видимости («Исходные слои» / «Сгенерированный план») в `ControlPanel.tsx` — по явной просьбе пользователя, вместо поддержки нескольких одновременных проектов (сознательно выбрано более простое решение).
- Полная сквозная проверка после всех правок: `pytest` 18/18, GeoJSON и DXF пути — upload → generate → validate (0 violations) → export, всё `HTTP 200`; `npm run build` без ошибок TypeScript.

## 2026-09-11 — Backend на асинхронной БД, история планов, ручное редактирование через UI

Контекст: пользователь заметил, что весь backend синхронный (эндпоинты, БД), попросил переделать на async везде, разобраться с «эвристика и ML путаются между собой» (оказалось — планы в БД/на карте, не сам скоринг) и продумать ручное редактирование плана.

- **БД переведена на настоящий async**: `asyncpg` + `AsyncSession` вместо `psycopg2`+`Session` (`backend/app/db/session.py`, `GREENPROJECT_DATABASE_URL` теперь `postgresql+asyncpg://...`). Все эндпоинты — `async def`. CPU-тяжёлые шаги (генерация плана, валидация, DXF) остались синхронными функциями, вызываются через `run_in_threadpool` — осознанно не `async def` с синхронным кодом внутри (заблокировало бы event loop) и не мультипроцессинг (оверкилл на этом масштабе). Подробности и весь класс багов `MissingGreenlet`, в который дважды упёрлись при переделке (ленивая подгрузка `plan.project`/`plan.items` после коммита не работает без `selectinload` заранее) — в `CLAUDE.md`.
- **Автоматическая живая проверка** (юнит-тестов на БД-слой не было и нет — писать их сейчас не просили): upload → generate (heuristic и ml) → list-plans → переключение между планами → 3 структурированные правки → validate → drag-правка → export, всё через реально поднятый `docker compose` стек. Ловила именно `MissingGreenlet` дважды подряд, оба раза до передачи пользователю.
- **«Путаница планов» — оказалась про историю, не про скоринг.** Каждый `generate` и так создавал новый `Plan` в БД (не перезаписывал), но фронт держал в состоянии только последний — переключаться между heuristic/ml-результатами было некуда. Добавлен `GET /api/projects/{id}/plans` (список без загрузки полных `items` — там могут быть сотни тысяч строк, отдельный `COUNT`-запрос) и секция «История планов» в `ControlPanel.tsx`.
- **Ручное редактирование — есть UI поверх уже существующего API.** Драг маркера уже был на бэкенде (`PATCH .../items/{id}`), просто не было фронта; структурированные операции (`убрать в радиусе`/`исключить полигон`/`заменить тип в зоне`) — тоже. Добавлены: клик по карте ставит центр/точки полигона (`MapView.tsx::EditLayer`, `useMapEvents`), панель выбора режима и параметров в `ControlPanel.tsx`, применение через уже существующий `edit-structured` эндпоинт.
- **Попутно найден и починен реальный, давно живущий баг**: правки координат с фронта приходят в WGS84 (родная CRS Leaflet), а хранится всё в `source_crs` проекта — раньше это было отмечено TODO как известный no-op, пока `source_crs` никогда не проставлялся. Теперь `EPSG:32637` — дефолт в UI, так что баг стал бы реальным (правки уезжали бы от остальной геометрии) без `geo_io.py::from_wgs84()`. Проверено: перепроецированные координаты drag-правки и структурированных операций возвращаются именно там, где кликнул пользователь.

## 2026-09-11 — Скруглённые углы зданий на карте и «долго грузит» — оба от одной причины

Контекст: пользователь прислал скриншот сгенерированного плана — "ну это явно не норм" — и пожаловался на медленную загрузку.

- **Скруглённые "блинчатые" углы зданий вместо прямоугольных.** С введением ненулевых отступов `lawn` от зданий (0.5м) их буфер стал видимым — а `shapely.buffer()` по умолчанию скругляет углы полигона (`join_style="round"`), так что вместо прямоугольной полосы отступа получался блин со скруглёнными углами (~130 точек контура вместо 5). Починено: для зон (здание/дорога — прямолинейные объекты) — `join_style="mitre"`, острые углы; для сетей (линии, могут гнуться) круглый оставлен как физически верный.
- **«Долго грузит» — не геометрия, запись в БД.** Профилировал `generate_plan` напрямую (временные `print` в контейнере): весь `geo_engine` (буферы/кандидаты/greedy-отбор) на 100×80м синтетике — 0.7-0.9с, а `session.add_all(rows)` + `commit()` для 2746 строк — **7.6 секунды** (~2.5мс на строку, батчинг INSERT'ов не срабатывал с ORM-объектами). Починено: `generate_plan` теперь пишет посадки одним Core bulk INSERT (`sqlalchemy.insert(PlantingItemRow), rows`) вместо поштучного ORM `add_all()` — на том же объёме укладывается в доли секунды.
- Оба фикса проверены на реально поднятом стеке (`docker compose`), `pytest` 20/20.
- **Третий фикс на ту же тему — ML-скоринг звал `predict_proba()` по кандидату, не батчем.** `ScoringStrategy`/`geo_engine.placement.ScoreFn` переведены на batch-сигнатуру (`score_fn(candidates: list) -> list[(score, rationale)]`, не по одному). `MLScorer.score_batch()` — один векторизованный вызов `predict_proba()` на весь список; было — вызов на каждого кандидата отдельно, замерено втрое медленнее (~5300 кандидатов: 9.5с против 0.8с батчем). `HeuristicScorer` не трогали — дефолтная реализация просто зовёт `score()` в цикле, там это и так дёшево.
- **Финальная (и самая крупная) находка — не баг кода вообще: раздутая dev-БД.** После фикса bulk insert `/generate` всё равно иногда занимал 8-10с — профилирование (ещё точнее, по каждому шагу `generate_plan`) показало, что сама вставка (`insert+commit`) нестабильно скачет от 0.2с до 8.4с, при том что весь остальной код — стабильно быстрый. Причина: за день интенсивного тестирования (мои curl-скрипты + прогоны пользователя через UI) в `planting_items` накопилось **1.5 млн строк, 553 МБ** — Postgres со случайным UUID PK вставляет тем медленнее, чем больше/более фрагментирован B-tree индекс. Проверил все 84 названия проектов в базе — все тестовые (`timing-test`, `profile-*`, дефолтное «Тестовая территория» из UI и т.п.), ничего похожего на настоящую работу пользователя. Получил явное подтверждение и почистил (`TRUNCATE ... CASCADE`) — таблица упала до 24 КБ, `insert+commit` вернулся к 0.2-0.3с, `/generate` целиком — **~1.5с для обоих режимов скоринга**. Команда на будущее — в `CLAUDE.md`.
- Вся временная `print`-профилировка убрана из кода после того, как нашли и починили реальные причины. Финальная сквозная проверка (после очистки БД): `pytest` 20/20, `verify_async_and_editing.py` — всё зелёное, heuristic и ml — оба ~1.5с на синтетике 100×80м.

## 2026-09-11 — Выделение видно поверх плана, массовое перемещение выделенных посадок

Контекст: пользователь протестировал прямоугольное выделение и попросил две вещи: (1) сделать так, чтобы прямоугольник был виден поверх точек плана (на плотной сетке он терялся под ними), (2) дать возможность сдвинуть все выделенные объекты разом одним движением.

## 2026-09-12 — Живой баг: «Восстановить» после удаления отказывало «за границей участка» на реальном CRS

Пойман пользователем на реальном проекте: удалил объекты, нажал «Отменить» в тосте — получил отказ (`OutOfTerritoryError`), хотя объект восстанавливался ровно на то же место, откуда был удалён мгновение назад. - **Причина — круговой проход через WGS84, когда `source_crs` реально задан.** `delete_items` снимает снэпшот через `geo_io.planting_items_to_geojson_dicts()` (репроекция `source_crs -> WGS84` — GeoJSON всегда в WGS84), `restore_items` перед проверкой/записью репроецирует его обратно (`from_wgs84`, `WGS84 -> source_crs`) — настоящий форвард+инверс через `pyproj.Transformer`, не no-op. Эмпирически измеренный шум кругового прохода на реальных UTM-масштабных координатах — ~1e-9 м на координату. Ничтожно на глаз, но `edit_service._assert_all_within_territory()` до этой правки использовала голый `shapely.within` без допуска: газон, вырезанный `buffers.buildable_area()` как `territory.difference(exclusion)`, по построению касается границы территории какой-то стороной, и вершина, сдвинутая на миллиардную долю метра наружу, делает весь полигон «не `within`».

- **Фикс** — `_assert_all_within_territory()` теперь проверяет `shapely.within` против территории, раздутой на `_TERRITORY_TOLERANCE_M = 1e-3` м (1мм), а не против точной границы. Раздутие территории, а не допуск по площади пересечения (как у `violation_mask`) — потому что `tree`/`shrub` восстанавливаются как точки, у которых нет площади для сравнения; раздутие работает единообразно и для точек, и для полигонов. 1мм — на три порядка больше шума репроекции и на три порядка меньше любой реальной дистанции правки (`canopy_radius`/`min_distance` — метрового масштаба), так что по-настоящему вышедшая за периметр правка по-прежнему отклоняется (проверено отдельно, до правки кода — скриптом на реальных координатах: газон на границе оживает после фикса, заведомо далёкий полигон остаётся отклонён).
- Регрессия — два новых теста в `TestRestoreItems` (`tests/test_api/test_edit_service.py`), впервые в этом классе с реальным `source_crs="EPSG:32637"` вместо `None`.

## 2026-09-13 (продолжение) — Отступ от границы участка, естественная расстановка вместо сетки

Контекст: после стресс-теста пользователь указал на два реальных пробела в модели генерации — деревья/кусты могли встать вплотную к границе участка (не газона — предыдущая правка про газон была верно отменена, дело было в самой территории), и расставлялись ровной математической сеткой. Обсудили и согласовали заранее (не бросился сразу писать код): значения отступа от границы — по масштабу как у дома; расстановка — Poisson-disc/blue-noise, не просто "покачанная" сетка.

- **Отступ от границы участка** — новый `planting_norms.yaml::territory_margin_m` (дерево 5.0м/куст 1.5м/газон 0.5м), `buffers.buildable_area()` получил параметр `territory_margin_m` и делает `territory.buffer(-margin)` до вычитания остального — геометрически другая операция, чем существующие `setbacks_m` (те раздувают препятствие и вычитают, тут нечего раздувать, нужно сжать саму территорию). Живая проверка на реальном курортном участке: ближайшее дерево оказалось на ~6.8м от границы двора, куст — ~1.55м, газон — ~0.50м (все ≥ настроенного отступа, газон практически впритык к своему собственному новому пределу — ожидаемо, он и есть весь остаток buildable-площади).
- **Естественная расстановка** — `candidates.py::generate_point_candidates` вместо `np.meshgrid` теперь кидает случайные точки (`rng.uniform`, векторизовано так же, как раньше сетка) с 4-кратным оверсэмплингом, а реальное прореживание делает уже существующий `placement.py::greedy_select` (у него и так есть буферизация по радиусу кроны + отклонение пересекающихся через пространственный хэш — ядро Poisson-disc "прими, если не пересекается с принятыми"). Осознанно не писали Бриджсона с нуля — подробное обоснование в `docs/decision_log.md`. На той же реальной территории: 149 позиций вместо прежних 108 (не на порядок меньше — оверсэмплинг 4x достаточен), расстояния между соседними деревьями — от 5.01м до 12.06м (не константные 5.0/7.07м, как была бы сетка) — визуально и численно подтверждённая не-регулярность.
- **Критично для воспроизводимости**: сид генератора не случайный — `pipeline_service._compute_planting_rows()` выводит его детерминированно из `zlib.crc32(f"{plan_id}:{planting_type}")`, так что `ensure_materialized()` (пересчёт схлопнутого плана) даёт байт-в-байт тот же результат, а не свежую случайную раскладку — иначе сломали бы существующую гарантию "план — чистая функция от рецепта".
- **Живая находка по пути, важнее самой фичи**: смена сетки на случайные точки впервые обнажила латентный баг в `placement.py` — буфер кроны считался с дефолтным `quad_segs=8` вместо `32` (как везде в `buffers.py`), и на грубом приближении окружности два круга-кандидата на расстоянии буквально 4.9963м вместо норматива 5.0м **не считались пересекающимися** — тест поймал это как провал `test_greedy_select_respects_species_spacing`. Сетка никогда не создавала кандидатов "на волосок" от порога (соседи по сетке — либо точно на шаге, либо диагональю дальше), поэтому баг тихо ждал в коде с самого начала. Починено — `quad_segs=32` и в `placement.py`. Заодно поднята точность теста (`_SETBACK_TOLERANCE_M=1e-3` вместо `1e-6`, который был безопасен только для сетки, не для реальной геометрической погрешности буфера).

**Три вещи, которые ломали текущий код, и что с ними сделано.**

- **Геометрия сетей лежит во вложенных блоках.** Геоподоснова выгружена из MicroStation (`msdElementTypeMultiLine`, `msdElementTypeLineString`), блоки вложены друг в друга. `read_dxf()` делал плоский `for entity in msp:` и для INSERT возвращал `None`: на эталонном листе modelspace держит 50 полилиний, а рекурсивное разворачивание даёт 6465 линейных объектов — то есть импортировалось меньше процента, молча и с видом успеха. Починено `iter_entities()` с рекурсией через `virtual_entities()` (`explode_blocks=True` по умолчанию), с ограничением глубины и глушением блоков, которые `ezdxf` развернуть не может. Отдельный случай — `SYMBOL_LAYERS`: у слоёв-символов (существующее дерево, колодец, люк, фонарь) точка вставки и есть объект, разворачивать их нельзя — получились бы кружки и чёрточки, из которых нарисован значок, вместо одного объекта.
- **Имена слоёв русские, а `DEFAULT_LAYER_MAP` английский.** Добавлен `MOSGEOTREST_LAYER_MAP` с реальными именами (воспроизведены дословно, включая опечатку апстрима «Опоры контакной сети» и вариант написания «Канализация самотечная» без «ё»), и `COMBINED_LAYER_MAP` — обе карты сразу, ключи не могут пересечься (одни ASCII-заглавные, другие кириллица). Слои, которые **не** маплены, перечислены с обоснованием прямо в модуле: «Трубопроводы»/«Подземные коммуникации» — общие свалки без указания среды, а выдуманный отступ применил бы неверный клиренс; «Граница улицы» — линия обмера, не полигон проезжей части. **Ошибочный вывод про границу участка — поймано вопросом пользователя, исправлено.** Сначала было записано: «пригодной границы в чертежах нет, обрывки в 2 и 5 вершин, настоящий контур в неподгруженном xref, вопрос к организаторам». Пользователь спросил «ты уверен, что этого нет в других папках?» — и оказалось, что не уверен и что вывод неверен. Проверены все 29 xref-файлов улицы (до этого конвертировались только `up`/`tp`/`brd`), и контур нашёлся прямо в поставке: `Xrefs/xref196297.dwg` (слой `!Граница работ`, 331 вершина, 29739 м²) и `Xrefs/xref192364.dwg` (361 вершина, 16132 м²), вместе 45870 м². Проверено, что это именно проектный участок, а не что-то похожее: внутри него 99.0% сохраняемых существующих деревьев, 99.0% проектируемых растений и 100% проектируемых деревьев. Ошибка была методологическая — вывод «данных нет» сделан по одному файлу, хотя соседние лежали в той же папке.

Что из этого следует в коде: **`read_dxf_bundle()`/`dxf_bundle_paths()`** — чтение чертежа вместе с его `Xrefs/` (конкатенация корректна, потому что все листы улицы в одной системе координат — проверено совпадением существующих деревьев между топопланом и дендропланом; в общем случае у xref бывают своя точка вставки/масштаб/поворот, и это оговорено в докстринге). Плюс два подвоха, каждый из которых по отдельности свёл бы находку на нет: контур нарисован полилинией с `is_closed=False` и разрывом концов 11 мм на периметре 1833 м (`_entity_to_geometry` дозакрывает такие — `_POLYLINE_CLOSE_TOLERANCE_M=0.05`, только при ≥4 вершинах и только если кольцо валидно, иначе остаётся линией); и `territory_polygon()` возвращала **первую** зону `territory`, что на этих данных дало бы либо обрывок-LineString, либо один полигон из двух, то есть молча потерянную треть участка — теперь объединяет все площадные и игнорирует неплощадные. `Граница заказа` с листов `brd` в карту слоёв намеренно не внесена: это объём заказанной съёмки (119011 м²), а не участок, и посадки уехали бы на соседний квартал. Живая проверка полного бандла (30 файлов): 10206 сшитых сетей всех шести типов, `territory_polygon()` отдаёт 45870 м².

**Две находки, вскрытые уже самой проверкой на реальных данных.** (1) **Баг в собственном коде:** `convert_with_libredwg` декодировал stderr конвертера строго как UTF-8, а `dwg2dxf` выводит туда пути и строки прямо из чертежа — в файлах из AutoCAD с русской локалью они не UTF-8. Обёртка падала `UnicodeDecodeError` на диагностике файла, который и так корректно отвергала (поймано живьём на `Xrefs/Освещение.dwg`, который LibreDWG честно не читает). Фикс — `errors="replace"`, регрессия в новом `tests/test_geo_engine/test_dwg_convert.py`. ## 2026-09-17 — Паттерны посадки: рядовая вместо россыпи

Контекст: пользователь сформулировал главную слабость алгоритма — «мы пока их просто нарандом тыкаем в соответствии с нормативными доками». Нормативное основание: 743-ПП п. 3.6.4 табл. 3.6.2 и МГСН 1.02-02 п. 4.2.9.2 описывают именно типы посадки (однорядная, двухрядная, групповая), а не россыпь. Схема выбирается `--pattern auto|scatter|row`, по умолчанию `auto` — ряд вдоль проездов, тротуаров и границы участка, россыпь в остатке.

**Три итерации, каждая после замера, а не догадки:**

1. Первая версия строила ряд вдоль каждого объекта-ориентира по отдельности. Замер показал, что рядов нет вообще: бортовой камень приезжает из чертежа **6510 отдельными отрезками**, буфер вокруг двухметрового огрызка почти круглый, и вдоль такого «ориентира» помещается одна точка. Добавлена сшивка ориентиров тем же `merge_dashed_lines`, что уже применялся к сетям, плюс отбрасывание остатков короче 15 м.

2. Вторая версия ставила ряд на кромку буфера самого ориентира. Юнит-тест вскрыл, что на площадке, где связывает отступ от границы участка (5 м у дерева) вместо дорожного (2 м), эта кромка лежит внутри запрещённой полосы и точек не даёт вовсе. Перешёл на край допустимой площади.

3. Замер после этого показал, что стало хуже по структуре: край допустимой площади извилист от вырезов под сети, ряд по нему рваный — медиана шага 12,8 м при нормативных 8, попаданий в норматив 14%. Итоговое решение — эквидистанта самого ориентира (гладкая, повторяет улицу), отодвигаемая наружу шагами до первой, на которой помещается ряд длиной хотя бы в два шага посадки.

**Итоговый замер на Песчаном переулке** (липа, шаг 8 м по классу кроны): рядовая посадка — 29 деревьев, медиана шага между соседями **8,11 м**, 56% в пределах ±0,5 м от норматива; свободная группа — 24 дерева, 12,56 м и 0%. Все 53 соответствуют нормативам.

Ориентирами берутся только улицеподобные объекты (проезжая часть, тротуар, трамвайное полотно, граница участка): ряд вдоль газопровода формально допустим, но это не аллея, а линия вдоль трубы. Отступ ориентира берётся через `resolve_setback` — он зависит от породы, и ряд по табличному значению оказался бы нарушением для крупнокронной. Россыпь идёт вторым проходом по площади за вычетом крон уже поставленного ряда: у каждого `greedy_select` свой пространственный индекс, общей памяти между проходами нет.

**Регрессия:** новый `tests/test_geo_engine/test_patterns.py` (17 тестов: шаг и центрирование ряда, сшивка фрагментированного бордюра, отбрасывание коротких остатков, только улицеподобные ориентиры, породный отступ, ряд на связывающем ограничении, россыпь не ложится на аллею, ряды проходят собственную проверку соответствия). `pytest` — 235 passed, 10 skipped (было 218).

## 2026-09-23 (продолжение 6) — Дорога/тротуар наконец стали настоящим препятствием, не только узкой полосой у борта

Пользователь прямо возразил на формулировку «вопрос ширины проезжей части пока открыт»: «берём тротуары и проезжую часть и отмечаем их у нас, мы же нашли их в автокаде, на них конечно же нельзя ничего выращивать». Стадийный замер разложил 124с: распаковка 0.66с, конвертация DWG→DXF 25.3с, чтение+сборка 94.7с (внутри — `stitch_utility_lines` 16.0с однопоточно). `docker stats` во время прогона показал неравномерность: пул чтения скачет между ~800% CPU (много мелких файлов параллельно) и ~90-95% (один воркер разбирает самый тяжёлый файл бандла, остальные семь простаивают).

Заодно найден факт, важный для любого будущего тюнинга производительности: полный текст ТЗ (раздел 3.1) задаёт целевую машину явно — **не менее 8 логических ядер, от 16 ГБ RAM (32 ГБ рекомендовано для тяжёлых DXF), Linux/МосТех.ОС**. Существовавший хардкод `_MAX_CONVERT_WORKERS`/`_MAX_READ_WORKERS = 8` в `dxf_reader.py` оказался НЕ случайным числом, а ровно этим гарантированным минимумом — совпадение молча ограничивало любую более мощную машину (12 ядер на деве) восемью воркерами, оставляя остальные ядра простаивать.

Реализованы все пять предложенных пользователем фиксов:

1. **`_bundle_pool_worker_count(n_files)`** — размер пула из `os.cpu_count()`, резервирует ядро под event loop только сверх гарантированного ТЗ-минимума (8 ядер и меньше — то же поведение, что раньше, без регрессии на минимальной машине).
2. **LPT-планирование** — сортировка по убыванию размера при отправке в очередь пула (для простого случая) и явный жадный бинпакинг `_lpt_partition()` (для батчинга, где бины нужно сформировать заранее) — доминирующий файл больше не остаётся один после того, как остальные воркеры уже освободились.
3. **`convert_with_oda_batch()`** — несколько DWG за один вызов ODA File Converter вместо одного вызова на файл. Замерено на 8 реальных мелких xref-файлах: 8 последовательных вызовов — 3.91с, один батч — 0.56с (**~7×**), подтверждает, что для мелких файлов почти всё время — фиксированный старт Qt6+xvfb, не сама конвертация.
4. **`stitch_utility_lines`'s профилирование нашло реальный оверхед** — 100 892 вызова `.buffer()` только чтобы задать область `STRtree`-поиска, хотя `STRtree.query()` без предиката сравнивает исключительно bbox (подтверждено чтением докстринга shapely). Заменено на `shapely.box(...)` той же протяжённости — идентичный результат, без построения круга. ~4.3с из ~16с прохода.
5. **`resolve_and_read_bundle()`** — новая функция, совмещающая конвертацию и чтение внахлёст: файл уходит в пул чтения сразу по завершении СВОЕЙ конвертации, не после всего батча. Порядок результата остаётся каноническим независимо от порядка завершения (регресс намеренно рассинхронизирует их и проверяет итоговый порядок).

**Живой результат на том же бандле, свежая сборка образа: 115с → 108с.** `docker stats` подтвердил более широкий параллелизм (кратковременный всплеск 1376-1432% CPU против прежних ~800%), но улучшение оказалось скромнее ожидаемого — прямое измерение показало новую причину: один конкретный DWG-файл этого бандла (21.5 МБ → 125.6 МБ DXF, 217К сущностей, 159К зон из HATCH/REGION-заливок) читается САМ ПО СЕБЕ 46.9с, почти половина всего времени, и никакая параллелизация между файлами это не сокращает — это стоимость одного файла на одном воркере. `cProfile` на чтении именно этого файла показал: узкое место — не код `geo_engine`, а собственный ASCII-токенайзер `ezdxf` (разбор группового кода на 217К сущностей), вклад shapely-вызовов на порядок меньше. Не исправлено, отдельно задокументировано в `CLAUDE.md` как следующий кандидат (гипотеза — бинарный DXF на выходе ODA парсился бы быстрее, не проверено эмпирически) — решение не принято, спросить пользователя перед тем, как вкладываться в эту, другую по масштабу задачу.
